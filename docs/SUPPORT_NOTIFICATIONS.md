# Support replies and notifications

Users submit the existing service contact forms. Tickets retain the authenticated creator UID and exact service key. Admin > Support provides Respond on each ticket; manual Log request has been removed. A response includes the original request context and is stored in admin_support_responses, keyed by a client-generated UUID for retry protection. Recipients and services are always derived from the original ticket, never from an email or values supplied by the response form. Legacy requests without a creator UID cannot be delivered in-app and return a clear error.

The related service dashboard shows a Notifications control. Unopened responses display a red badge and red light. Opening an individual response marks it read, removes its unread count and shows a green light. Merely opening the notification tray does not mark all responses read. Helpful and Not helpful buttons persist the selected feedback, and users can change their choice. Clear notification dismisses that response for its owner while retaining the ticket, response, read receipt and feedback for admin. A later admin response creates a new unread notification.

Admin Support shows read status and latest user feedback; Respond opens the conversation with per-response receipts and feedback, including cleared responses. Support lists and open response forms refresh every 15 seconds. User notifications refresh every 15 seconds, on focus and after actions. Notifications are in-app only; no email or WhatsApp message is sent. All six service dashboards share the same component without altering their business handlers. General/legacy blood/organ support replies appear on the Services hub. The server returns the latest 100 active notifications for a selected scope with its total unread count.

GET /api/admin/support/notifications?service=... and PATCH /api/admin/support/notifications/{id} require a valid signed-in account and enforce ownership. The GET response is private/no-store. PATCH accepts read, clear, helpful or not_helpful. Administrator-only GET /api/admin/support/{ticket}/responses and POST /api/admin/support/{ticket}/respond provide conversation access and sending. Repeated sends with the same request ID and message do not create duplicate notifications. Changing that message while reusing an ID is rejected. Access does not rely on hiding buttons.

Medicine catalogue Pending now displays as Not reviewed. Verification flags and the clinical reviewer permission requirement are unchanged. Internal resolution notes in Manage are not delivered; use Respond to send a user-visible message.

Restart the backend and refresh the frontend after deploying. MongoDB creates the response collection on first use; no new provider or credential is required. Tests use synthetic tickets and isolated mocked browser sessions and do not send replies to real users.
